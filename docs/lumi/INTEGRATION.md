# Lumi: real stored-data integration

## Diagnosed 404
LumiWidget requests GET /api/lumi/v1. The frontend wildcard rewrite forwards /api/* to BACKEND_URL. Both localhost:3000/api/lumi/v1 and the configured Netlify backend returned HTTP 404, text/html, Server: Netlify. The backend had no route at that path. Python implements a DIFFERENT private contract: POST /v1/session with timestamped HMAC. No public backend adapter existed.

## Contract and trust boundary
GET /api/lumi/v1?meterId=... loads analysis, events and conversation. POST same URL supports chat, label, read, clear, preferences and goal. Only action fields are accepted: browser context/userId/readings are rejected. Optional from/to ISO timestamps select an interval, end excluded, within the last 60 days. The server validates the Supabase session with getUser, resolves membership using the existing owner/member repository, and refuses an inaccessible meter with 403 before querying readings. Omitted meter selects the same default as existing dashboard APIs. All meter dashboard APIs now accept the same authorized selection hint.

The backend reads the existing readings table with device_id and time filters, pages 1000 rows at a time, caps the latest 60000 observations, and marks truncation. It also retrieves the same stored latest reading used by the meters dashboard. It never invokes Tuya for Lumi. No new collector, production writes, new RLS policy or language model provider is added. Machine learning computes energy/profile/observations; it never gets Supabase credentials or browser cookies.

The signed body includes only the validated user, authorized meter, metadata and that meter's stored observations. HMAC-SHA256 covers timestamp, path and exact JSON bytes; the Python service accepts a 60-second clock tolerance. No shared analysis cache or background job was introduced. Responses are private/no-store, with context verified again on return from Python.

Python SQLite persists conversation, event labels/read flags, preferences and personal Lumi goal using BOTH user and meter keys. An explicit Lumi goal is personal. Otherwise the existing Proyección goal is imported only for its owner; a shared member never inherits the owner's personal goal. Original dashboard goals/settings retain their existing installation semantics. An LLM is not configured: responses explicitly use structured analytical rules.

## Running locally / deployment
1. Python project: configure a unique private LUMI_SERVICE_SECRET of at least 32 characters and durable LUMI_DB_PATH (outside git); run python -m lumi.server. Local default bind is 127.0.0.1:8010. Install requirements, including timezone data on Windows.
2. Backend: configure the SAME secret, LUMI_SERVICE_URL pointing at that Python service, and comma-separated LUMI_ALLOWED_ORIGINS including the frontend origin (port included). Existing Supabase server environment remains necessary. Run backend on a distinct port, e.g. npm run dev -- --port 3001.
3. Frontend: BACKEND_URL=http://localhost:3001; restart development server. Or deploy this backend route to the existing BACKEND_URL first. Keeping the old published backend will keep returning 404 regardless of frontend changes.
4. Netlify cannot execute this persistent Python HTTP/SQLite process inside the Next backend. Deploy ML independently with private TLS access and a durable SQLite volume (one service instance), set its URL and shared secret in backend environment, and deploy backend and frontend separately to their own repositories. The ML service has no browser-facing endpoint.

Frontend navigation carries meterId. A user/meter keyed context boundary unmounts old visible data and requests; auth changes hide the prior context and redirect. Lumi aborts old requests, checks controller identity before accepting results, and clears stale sensitive UI on 401/403. Selection does not key the floating character by analysis state, so polling does not restart flotation.

## Verification and limits
Tests use a temporary SQLite database, two fixture identities and four meters (including an authorized shared meter). They execute the real Next route, real guard and HMAC client, and real Python HTTP/analytics/storage. Only validated auth and stored reading source are fixture adapters. Assertions cover latest value/unit/date/meter, 1.250 kWh defined-period calculation, persisted conversation, separate personal goal/preferences, meter switch, forbidden cross-user access before reading queries, tampered context rejection, origin rejection, expired session and explicit missing configuration. Set LUMI_TEST_PYTHON to the Python executable to enable the real-service integration test when running npm test; without it, that cross-project test is explicitly skipped. Separate source-adapter tests verify device/time filters and pagination past 1000 rows. Existing backend and Python tests are also run.

These tests DO NOT establish a connection to production data. Published backend and ML service configuration/deployment are still required. No production accounts, production database changes or credentials were used in fixture tests. Browser verification against live authenticated data remains pending until the service is available. A maximum-60-day/capped analysis is not a full historical archive; truncation is declared and forecasts suppressed for truncated data. Latest readings and basic calculations work without model training. Conversations and readings remain distinct resources; clearing conversation never deletes readings.

Validation on this workspace: 233 backend tests passed with the real-service integration enabled; 24 Python tests passed; frontend TypeScript and backend source/tests TypeScript passed; ESLint passed; frontend 11 state checks and 7 conversation/avatar checks passed. A complete backend project typecheck/build remains blocked by the absent @netlify/functions dependency; source/tests were checked with the existing compatible frontend dependencies temporarily linked, then the link removed. Browser/live-data validation was not performed.
